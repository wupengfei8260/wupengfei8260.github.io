# 本项目智能体实施蓝图

## 1. 目标与范围

目标：在当前仓库内建立一个可复用的智能体工作流，稳定产出以下内容。

- 前端需求文档三件套：代码对齐版、评审版、接口化改造版
- PRD 与代码一致性审查
- 可选：CSV 调研表质量校验与补全建议（默认关闭）

项目范围：

- 页面与模块代码目录：modules/
- 文档目录：docs/
- 页面入口：index.html

非范围：

- 不自动发布线上
- 不自动修改后端接口
- 不在缺少证据时编造结论

## 2. 智能体角色定义

### 2.1 主智能体（编排者）

职责：

- 接收任务目标并拆解子任务
- 调用代码分析、文档生成与一致性审查流程
- 统一落盘到 docs/ 对应目录
- 输出执行报告（做了什么、改了什么、待确认什么）

输入：

- 任务说明（中文）
- 目标模块路径
- 目标输出类型

输出：

- 结构化文档文件
- 执行摘要

### 2.2 子智能体 A：代码对齐文档助手

职责：

- 读取指定模块代码
- 提取页面结构、交互流程、状态字段、事件链路
- 产出代码对齐版与评审版草稿

### 2.3 子智能体 B：接口化改造助手

职责：

- 从代码与文档中提取接口需求
- 标注现状（硬编码、本地 mock、字段缺失）
- 产出接口清单与改造优先级

### 2.4 子智能体 C（可选）：调研表质检助手

职责：

- 检查 CSV 必填字段完整性
- 识别待补充、待校验条目
- 生成补全建议，不伪造来源

## 3. 输入输出模板（直接可用）

### 3.1 任务输入模板

```
任务类型：文档三件套 / 一致性审查 / 可选CSV质检
目标模块：modules/home/dailyReview
页面入口：index.html
参考文档：docs/home/*.md
输出目录：docs/home/
约束：不编造；信息不足标注“待补充”；保留现有命名
```

### 3.2 文档输出结构模板

代码对齐版：

- 背景与目标
- 页面结构与模块划分
- 核心状态与字段说明
- 关键交互与时序
- 异常与兜底
- 与现有实现差异

评审版：

- 需求摘要
- 评审关注点
- 业务风险
- 技术风险
- 测试要点
- 待确认问题

接口化改造版：

- 改造目标
- 接口清单（入参、出参、错误码、超时策略）
- 前端改造点
- 回滚策略
- 里程碑计划

- docs/home/**

## 5. 两个核心工作流 + 一个可选工作流

### 工作流 1：文档三件套自动产出

触发条件：

- 新需求立项
- 页面有明显改动
- 评审前补齐资料

建议输入示例：

```
为 modules/home/dailyReview 生成代码对齐版、评审版、接口化改造版，
输出到 docs/home/，并与已有 home 文档合并去重。
```

目标输出文件：

- docs/home/代码对齐版-前端需求文档.md
- docs/home/评审版-前端需求文档.md
- docs/home/接口化改造版-前端需求文档.md

验收标准：

- 三份文档均含目录和章节
- 关键字段有来源定位
- 不与现有章节冲突

### 工作流 2（可选）：CSV 调研表质检与补全建议

触发条件：

- 新增调研条目
- 周期性巡检

建议输入示例：

```
检查 docs/data/顺丰小哥APP_AI功能调研表.csv 的完整性，
输出“缺失字段清单 + 可补证据建议 + 待校验项列表”。
```

当前样例文件说明：

- 发现第一条记录大部分字段为空
- 校验状态为“待补充”
- 备注提示“请填入可核验来源后更新”

验收标准：

- 输出缺失字段列表
- 对每条缺失给补充建议
- 不自动伪造来源链接

### 工作流 3：PRD 与代码一致性审查

触发条件：

- 需求评审前
- 提测前

建议输入示例：

```
审查 docs/home/复盘日报实时推送业务员-PRD.md 与 modules/home/dailyReview/** 的一致性，
输出“已实现 / 部分实现 / 未实现 / 命名不一致”四类结果。
```

重点对齐对象：

- docs/home/复盘日报实时推送业务员-PRD.md
- docs/home/复盘日报_今日明细／昨日汇总.md
- modules/home/dailyReview/index.js
- modules/home/dailyReview/reviewDaily.js
- modules/home/dailyReview/reviewDailyYd.js
- modules/home/dailyReview/yesterday.js

验收标准：

- 给出差异点与证据位置
- 给出修复优先级
- 输出待确认问题清单

## 6. 标准执行口令（可直接复用）

### 6.1 生成 home 三件套

```
基于 index.html 与 modules/home/**，
产出 docs/home/ 下的代码对齐版、评审版、接口化改造版。
要求：与现有文档去重合并；保留业务术语；所有结论可定位到代码或文档。
```

### 6.2 跑 CSV 质检

```
对 docs/data/顺丰小哥APP_AI功能调研表.csv 做字段完整性检查，
输出缺失项、风险项、待补证据项，并生成补全建议。
要求：不编造来源，无法确认则标注待补充。
```

### 6.3 跑一致性审查

```
对 docs/home/*.md 与 modules/home/dailyReview/** 做一致性审查，
输出差异表（已实现/部分实现/未实现/命名不一致）与修复建议。
```

## 7. 建议的落地节奏（7 天）

第 1-2 天：

- 固化输入输出模板
- 先跑通工作流 1（home 模块）

第 3-4 天：

- 可选上线工作流 2（CSV 质检）
- 可选补充调研表字段规范

第 5-6 天：

- 上线工作流 3（一致性审查）
- 增加风险等级标记

第 7 天：

- 回顾产出质量
- 固化常见问题处理规则

## 8. 失败兜底策略

- 证据不足：仅输出“待补充 + 需要的证据类型”
- 路径不存在：输出“路径校验失败 + 建议路径”
- 文档冲突：保留原文并输出冲突片段对照
- 字段无法映射：标注“人工确认”而非自动猜测

## 9. 本项目首批执行清单

- 先执行：home 三件套增量更新
- 再执行：home PRD 与 dailyReview 代码一致性审查
- 可选执行：AI 调研 CSV 质检报告

交付目标：

- 当天可用于评审
- 第二天可用于开发排期

## 10. 自动同步需求文档（改代码/改功能描述后触发）

结论：可以设定自动修改需求文档，建议采用“开发期实时触发 + 提交前兜底触发”双轨模式。

### 10.1 触发源

代码触发：

- 监听 modules/home/**
- 监听 modules/mustSign/**
- 监听 modules/consult/**

功能描述触发：

- 监听 docs/home/*.md
- 监听 docs/mustSign/*.md
- 监听 docs/consult/*.md

### 10.2 双轨触发模式

模式 A（开发期）：保存即触发

- 适用于高频改动期
- 每次保存后执行“增量文档同步”
- 输出到对应 docs 子目录

模式 B（提交流程）：提交前触发

- 适用于稳定交付期
- 在 commit 前统一执行“文档一致性检查 + 自动修订”
- 阻止遗漏文档变更进入主分支

### 10.3 本项目推荐映射规则

- modules/home/** -> docs/home/**
- modules/mustSign/** -> docs/mustSign/**
- modules/consult/** -> docs/consult/**

特殊场景：

- 当变更目录为 modules/home/dailyReview/** 时，同时触发 docs/home/ 下三件套更新
- 当变更为 PRD 文档时，触发对应模块一致性审查，不直接覆盖代码对齐版正文，先输出差异清单

### 10.4 自动更新时的防误改策略

- 仅更新“自动维护区块”（如章节：实现状态、字段清单、差异表）
- 人工撰写区块（背景、结论、业务判断）默认不覆盖
- 发生冲突时生成“冲突对照段”，等待人工确认后合并

### 10.5 验收标准

- 代码变更后 1 次触发内完成文档增量同步
- 文档与代码差异项可追踪到文件位置
- 不出现无证据结论
- 提交前检查可阻断“代码变更但文档未更新”的情况

### 10.6 一句话执行口令（自动同步版）

开发期：

保存代码或功能描述后，自动扫描本次变更文件，按目录映射增量更新对应需求文档，并输出差异摘要与待确认项。

提交流程：

提交前自动执行文档一致性检查；若存在未同步差异，则先自动修订自动维护区块，再输出人工确认清单。

### 10.7 既有需求文档基线策略（home）

规则：

- 仅 dailyReview 模块变更时，优先在既有需求文档上增量修改
- 基线文档为 docs/home/复盘日报_今日明细／昨日汇总.md
- 基线更新完成后，再同步 docs/home/ 下三件套
- 自动流程仅写入“自动维护区块”，不覆盖人工正文

不触发基线文档的变更：

- modules/home/mustSign/**
- modules/home/signedReport/**
- 其他与 dailyReview 无关的 home 子模块

建议口令：

请以 docs/home/复盘日报_今日明细／昨日汇总.md 为基线进行增量修改，保留原章节结构；仅补充变更影响、字段差异、待确认项，并同步三件套自动维护区块。

## 11. CSV 子智能体是否需要（本项目口径）

结论：默认不需要，按需启用。

默认关闭原因：

- 本项目主目标是“代码与需求文档同步”，CSV 不属于主交付链路
- 常驻 CSV 子智能体会增加任务路由复杂度与维护成本
- 对提交前自动同步价值有限，容易引入无关噪音

建议启用条件：

- 需要周期性输出调研质量报告
- CSV 结论将直接进入本项目评审文档
- 需要把外部调研数据固化为可追溯证据链

不启用时的替代方案：

- 临时会话模式按次执行 CSV 质检
- 仅保留口令模板，不加入默认流水线

## 12. 如何复用到其他模块（以 mustSign 为例）

结论：采用“模块路径 + 基线文档 + 自动维护区块”三段式复用。

### 12.1 复用步骤

- 第一步：确定模块范围（例如 modules/home/mustSign/**）
- 第二步：指定该模块的基线文档（例如 docs/mustSign/电话勿扰上报原因-PRD.md）
- 第三步：保留自动维护追踪文档（docs/mustSign/自动维护-变更追踪.md）
- 第四步：触发后先更新基线文档自动维护区块，再更新追踪文档

### 12.2 本项目已落地映射

- dailyReview：modules/home/dailyReview/** -> docs/home/复盘日报_今日明细／昨日汇总.md
- mustSign（子功能级）：
- abnormal -> docs/mustSign/电话勿扰上报原因-PRD.md
- dispatch -> docs/mustSign/晚间时段电联提醒-PRD.md
- signed -> docs/mustSign/电话勿扰上报原因_1-PRD.md
- third -> docs/mustSign/晚间时段电联提醒-PRD.md
- zcw -> docs/mustSign/晚间时段电联提醒-PRD.md

### 12.3 扩展到新模块的方法

- 在脚本中新增一个 BASELINE_DOC 变量
- 在变更识别中新增对应模块文件匹配规则
- 新增对应同步函数，保持“基线优先，追踪兜底”
- 语法校验通过后纳入提交前检查

### 12.4 mustSign 两种组织方式（都支持）

方式 A：每个子功能一个文档

- 给每个子功能单独指定基线文档
- 适合评审口径严格隔离的场景

方式 B：多个子功能共用一个文档

- 将多个子功能映射到同一个基线文档路径
- 适合功能耦合高、统一评审的场景

可复制配置（环境变量覆盖）：

```
MUSTSIGN_DOC_ABNORMAL=docs/mustSign/电话勿扰上报原因-PRD.md
MUSTSIGN_DOC_DISPATCH=docs/mustSign/晚间时段电联提醒-PRD.md
MUSTSIGN_DOC_SIGNED=docs/mustSign/电话勿扰上报原因_1-PRD.md
MUSTSIGN_DOC_THIRD=docs/mustSign/晚间时段电联提醒-PRD.md
MUSTSIGN_DOC_ZCW=docs/mustSign/晚间时段电联提醒-PRD.md
```

说明：

- 不需要每个文档重复声明智能体
- 只需维护脚本里的映射关系，智能体会自动路由到对应文档

## 13. 分期模块治理规则（防止信息丢失）

目标：一期只做部分指标时，仍保留二期指标定义，避免后续重写。

执行规则：

- 每个主需求文档新增“分期管理模块”
- 智能体仅更新分期状态、分期记录、自动维护区块
- 非本期指标正文不删改，最多标记状态为“待排期/暂缓”
- 本期范围变更必须记录在“分期变更记录”中

推荐口令：

请基于当前需求文档执行分期增量更新：仅更新分期模块与自动维护区块，不删除非本期指标正文；将未纳入本期的指标统一标记为待排期。
